# 議事録作成Agent Skills群 構築仕様書

## Master Specification v1.0

## 0．本仕様書の位置づけ

本仕様書は、録音音声およびユーザーから提供された関連資料を根拠として、正確性・検証可能性・可読性を備えた議事録を作成するための**Agent Skills群一式をAIに構築させるための実装仕様書**である。

本仕様書を受け取ったAIは、単一の巨大なSkillを作成するのではなく、責任範囲を分離した複数のSkills、共通ルール、テンプレート、CSS、補助スクリプト等から構成される一つのSkillシステムを構築すること。

第一の利用環境としてChatGPT Workを想定する。

ただし、Skillの中核ロジックは特定プラットフォームへ依存させず、Claude、Geminiその他Agent Skills対応環境へ移植できる構造とする。

------

# 1．目的

本Skills群の目的は、会議、打合せ、学習会、研修会、座談会、意見交換会、説明会等について、

- 録音音声
- ユーザーから提供された資料
- 参加者情報
- 議案書
- レジュメ
- その他の関連資料

を根拠として、**根拠を追跡可能な議事録を作成すること**である。

音声から直接完成議事録を一度に生成してはならない。

以下の工程を分離する。

1. 音声を記録する
2. 会話の構造を把握する
3. 議事内容の意味を整理する
4. 読者向け議事録へ編集する
5. 全工程を統括・検証する

各工程では独立した成果物を作成し、Work等の作業領域に保存する。

------

# 2．設計思想

本システムでは、

> AIに正しい議事録を一発で書かせる

ことを目的としない。

人間が議事録を作成するときに行う、

**原記録を残す
 → 内容の構造を把握する
 → 議事内容を整理する
 → 根拠を確認する
 → 読者向けに編集する
 → 必要なら原記録へ戻る**

という工程をAgent Skillsとして再現する。

AIには各工程で必要な判断を行わせるが、**判断の根拠を失わせないことを最優先する。**

------

# 3．全体処理フロー

```
原音声 ───────────────┐
                       │
提供資料 ──────────────┤
                       │
                       ▼
              Skill 02
       音声トランスクリプト
                       │
                       ▼
              Skill 03
           シーン構造分析
                       │
                       ▼
              Skill 04
            議事内容整理
                       │
                       ▼
              Skill 05
             議事録作成
                       │
                       ▼
              Skill 01
             最終品質確認
```

Skill 01は実際には全工程を最初から最後まで統括する。

したがって論理的には、

```
Skill 01：統括
   │
   ├─ Skill 02
   ├─ Skill 03
   ├─ Skill 04
   └─ Skill 05
```

という関係になる。

meeting-minutes-writer

**Skill 02～04および提供資料を根拠として、読者向けの正式な議事録を作成する。**

# 6．共通基本原則

すべてのSkillsは以下の原則に従う。

## 6.1 根拠主義

議事録に含める、

- 事実
- 発言
- 説明
- 報告
- 質問
- 回答
- 意見
- 評価
- 懸念
- 提案
- 合意
- 確認
- 決定
- 対応事項

等は、原則として提供された情報から確認できるものに限定する。

AIの一般知識、学習済み知識、推測等によって、会議内容を追加してはならない。

------

# 7．利用可能な情報源

原則として以下を利用する。

### 一次情報

- 原音声
- ユーザーが提供した資料

### 派生情報

- Skill 02 Transcript
- Skill 03 Scene分析
- Skill 04 議事内容整理

ユーザーから明示的に指示されない限り、議事録作成のためにウェブ検索その他の外部情報を追加してはならない。

------

# 8．EvidenceとReference

情報源を可能な限り以下の二つに区別する。

## Evidence

当該発言、説明、確認、合意、決定等が実際に存在したことを直接確認する根拠。

例：

- 原音声
- Transcript
- 会議中に明示的に確認された資料

------

## Reference

名称、数字、制度、日付、表記、背景等を確認・補完する資料。

例：

- 配布資料
- 議案書
- 説明資料
- レジュメ
- 出席者名簿

------

# 9．Referenceの禁止用途

Referenceに記載されているという理由だけで、

- 会議で説明された
- 出席者が了承した
- 認識が共有された
- 合意された
- 決定された
- 実施することになった

等と認定してはならない。

会議上の意思形成についてはEvidenceを必要とする。

------

# 10．中間成果物の位置づけ

Skill 02～04の成果物は重要な作業資料であるが、原音声そのものではない。

したがって、

> 前工程に書いてあるから正しい

という扱いをしてはならない。

特に以下について疑義がある場合は、Transcriptまたは原音声へ遡る。

- 決定
- 合意
- 担当者
- 期限
- 数値
- 金額
- 日付
- 固有名詞
- 発言者
- 賛否
- 条件
- 留保

------

# 11．必要箇所参照の原則

長大なTranscript、資料、中間成果物について、後工程が毎回すべてを全文再読込することを原則としない。

基本処理は、

```
構造化成果物
↓
必要なSceneまたはM-IDを特定
↓
該当Transcript範囲を確認
↓
必要な場合のみ原音声へ遡る
```

とする。

例えば、

```
M-032
↓
S-011
↓
Transcript 00:42:15～00:44:03
↓
必要なら原音声 00:42:15～00:44:03
```

と参照する。

ただし、コンテキスト節約を理由として必要なEvidence確認を省略してはならない。

**効率より正確性を優先し、不必要な全文再読込のみを避ける。**

------

# 12．不確実性の保持

確認できない情報を推測によって確定しない。

必要に応じて、

- 不明
- 聞き取り不能
- 聞き取り不確実
- 話者不明
- 要確認
- 明示的な決定を確認できず

等として保持する。

自然な文章にすることを理由として不確実性を削除してはならない。

------

# 13．成果物

以下を独立した成果物として保存する。

```
01_音声トランスクリプト.md
02_シーン構造分析.md
03_議事内容整理.md
04_議事録.md
minutes.css
```

各成果物は後工程の一時情報として破棄せず、人間が必要に応じて確認・修正できる状態を維持する。

------

# 14．Skill 01：meeting-minutes-orchestrator

## 14.1 目的

ユーザーから録音・資料を受け取り、Skill 02～05の処理を統括する。

ユーザーが例えば、

> この録音と資料から議事録を作成して。

と依頼した場合、本Skillが起点となる。

------

## 14.2 入力確認

利用可能な、

- 音声
- 資料
- 会議名
- 日時
- 開催形式
- 出席者情報
- その他関連情報

を確認する。

情報が不足していても処理可能な場合は、作業を継続する。

不明事項は後工程で不明・要確認として扱う。

ユーザーへの質問は、処理そのものが不可能な場合または重大な判断が必要な場合に限定する。

------

# 15．Skill 01の処理順序

原則として、

1. 入力確認
2. Skill 02実行
3. `01_音声トランスクリプト.md`保存
4. Skill 03実行
5. `02_シーン構造分析.md`保存
6. ID点検
7. Skill 04実行
8. `03_議事内容整理.md`保存
9. ID・参照関係点検
10. Skill 05実行
11. `04_議事録.md`保存
12. 最終ID・参照関係点検
13. 内容品質検証
14. ユーザーへの結果報告

とする。

------

# 16．Skill 01の最終報告

作業終了時には最低限、

- 議事録が完成したこと
- 中間成果物が保存されたこと
- 要確認事項の件数
- 特に確認が必要な事項

を簡潔にユーザーへ示す。

要確認事項がない場合は、その旨を明示してよい。

------

# 17．Skill 02：audio-transcript

## 17.1 目的

音声を、後工程で根拠として利用できるTranscriptへ変換する。

本Skillは、

> **何と言ったか**

のみを扱う。

意味分析は行わない。

------

# 18．Transcript基本処理

- 原音声の時系列を保持する。
- 適切な間隔でタイムスタンプを付ける。
- 可能な範囲で話者を識別する。
- 発言の意味を保持する。
- 適切な句読点・改行を付与する。
- 意味を持たないフィラーは必要に応じて整理できる。
- 言い直しは意味を損なわない範囲で整理できる。

------

# 19．話者識別

以下のような根拠がある場合は氏名を記録する。

- 本人が名乗った
- 司会者等が明示的に指名した
- 会話上、合理的かつ明確に特定できる

それ以外は、

- 話者A
- 話者B
- 話者不明

等とする。

------

# 20．参加者資料による氏名補正

参加者名簿等は、氏名の正式表記を確認するために使用できる。

例えばTranscriptが、

> 山崎

と認識しており、参加者資料に、

> 山嵜

と記載され、同一人物であることが合理的に確認できる場合は、

> 山嵜

へ補正してよい。

ただし、

> 参加者名簿に山嵜氏がいる
>  → この声は山嵜氏だろう

という推定は禁止する。

------

# 21．不明瞭箇所

聞き取れない部分を文脈から創作しない。

以下を利用する。

```
[聞き取り不能]
[不明]
[聞き取り不確実：○○？]
```

------

# 22．Skill 02禁止事項

以下を行わない。

- 要約
- Scene分類
- 論点整理
- 発言重要度判定
- 意見・提案・決定等の意味分類
- 一般知識による補完
- 不明話者の推定
- 不明な数字・名称等の断定

------

# 23．音声処理能力がない環境

プラットフォームが音声処理に対応していない場合、

**処理したふりをしてはならない。**

利用可能な、

- 音声文字起こし機能
- 外部Transcript
- ユーザー提供Transcript

等へ切り替える。

------

# 24．Skill 03：meeting-scene-analyzer

## 24.1 目的

Transcriptを、

> **どの時間帯に、どのような機能で、何について話していたか**

という観点からSceneへ構造化する。

------

# 25．Scene ID

各Sceneに、

```
S-001
S-002
S-003
...
```

を時系列順に付与する。

------

# 26．Scene大分類

## A．進行・運営

例：

- 開会
- 挨拶
- 趣旨説明
- 日程説明
- 休憩
- 閉会

## B．情報提供・説明

例：

- 議案提起
- 経過説明
- 制度説明
- 講演
- 資料説明
- 情勢説明

## C．質疑・理解確認

例：

- 質問
- 回答
- 事実確認
- 補足説明

## D．実態・経験共有

例：

- 職場実態
- 活動報告
- 事例紹介
- 体験談

## E．意見・論点共有

例：

- 意見
- 評価
- 問題提起
- 懸念

## F．検討・協議

例：

- 対応方針検討
- 選択肢比較
- 議案協議
- 対応方法検討

## G．取りまとめ・方向性確認

例：

- 議論の整理
- 今後の取扱い確認
- 方向性確認

**Gに分類したこと自体は、合意・決定が成立したことを意味しない。**

合意・決定の認定はSkill 04のみが行う。

------

# 27．サブ分類

サブ分類は固定リストに限定しない。

内容に応じて生成する。

例：

```
大分類：情報提供・説明
サブ分類：2026年人事院勧告の概要説明
```

------

# 28．Scene分割基準

話者が交代しただけでは分割しない。

以下のいずれかが実質的に変化した場合にSceneを切り替える。

- 会話の主要機能
- 主要テーマ
- 主要論点
- 会議・行事上の段階

同じテーマでも、

```
説明
↓
質疑
↓
実態共有
↓
意見交換
↓
協議
```

と機能が変化すれば別Sceneとしてよい。

------

# 29．Skill 03標準出力

```
## S-005

- 大分類：実態・経験共有
- サブ分類：再任用職員の処遇に関する各職場の状況
- 時間：00:32:15～00:38:20
- 主要テーマ：
  - 再任用職員
  - 給与改定
- 主な話者：
  - 山嵜
  - 話者B
- 根拠：
  - Transcript 00:32:15～00:38:20
```

------

# 30．Skill 03禁止事項

個々の発言について、

- 意見
- 提案
- 賛成
- 反対
- 合意
- 決定

等の意味認定を原則として行わない。

Scene分類のための会話機能判定に留める。

------

# 31．Skill 04：meeting-content-analyzer

## 31.1 目的

TranscriptおよびScene分析から、

> **何が説明され、問われ、報告され、意見・提案され、確認・決定されたか**

を整理する。

完成議事録は作成しない。

本成果物は**議事内容台帳・監査台帳**として機能する。

------

# 32．Meaning Unit

議事内容の基本単位を、

**Meaning Unit**

とする。

各Meaning Unitには、

```
M-001
M-002
M-003
...
```

を付与する。

------

# 33．Meaning Unitの判定

M-IDは個々の発言ごとに付与するのではない。

以下のような、

> 一つの主張、情報、質疑、検討、合意、決定または対応として扱うことが適切な「議事上の意味まとまり」

ごとに付与する。

例えば、

```
現状
↓
理由
↓
評価
↓
意見
```

が一つの主張を構成している場合は、一つのM-IDにまとめてよい。

一方、

```
意見
↓
提案
↓
合意
↓
決定
```

のように議事上の状態が実質的に変化した場合は分割する。

判断に迷う場合は、**過度な細分化より文脈保持を優先する。**

------

# 34．M-IDの時系列

M-IDは原音声上で登場した順番に付与する。

表示上、後に論点別へ並べ替えてもM-IDを変更しない。

同一論点が会議後半に再登場した場合も新しいM-IDを付与する。

------

# 35．Meaning Unit属性

必要に応じて、

- 説明
- 事実・経過報告
- 質問
- 回答
- 実態報告
- 意見
- 評価
- 懸念
- 提案
- 反対意見
- 確認
- 合意
- 決定
- 継続協議
- 対応事項
- その他

を使用する。

複数属性を付与してよい。

------

# 36．確実性

Meaning Unitには原則として以下のいずれかを付与する。

## 確定

Transcriptまたは原音声等から明確に確認できる。

## 補完あり

発言内容自体は確認できるが、正式名称、数字、氏名表記等を提供資料によって補完した。

## 要確認

- 複数の解釈が可能
- 聞き取り不明瞭
- 発言者不明
- 決定成立の有無が不明
- 資料と発言が矛盾

等により確定できない。

Skill 05は「要確認」のM-IDを確定事項として扱ってはならない。

------

# 37．Skill 04における資料補完

Skill 04で資料を使用する目的は、

> **発言・議事内容を正しく認定するため**

である。

補完可能な例：

- 人名
- 組織名
- 制度名
- 文書名
- 数字
- 日付
- 専門用語

------

# 38．資料と発言の矛盾

資料とTranscriptが矛盾する場合、勝手に整合させない。

例えば、

```
資料：9月実施予定
発言：10月で調整する
```

なら、

> 資料では9月、会議中の発言では10月となっており、最終時期は要確認。

とする。

------

# 39．Skill 04標準出力

```
### M-014

- Scene：S-005
- 属性：
  - 実態報告
  - 意見
- 発言者：山嵜
- 内容：
  - 当局から具体的な説明がまだ示されていない。
  - 前年の対応も遅かったことから、今年は早期に確認した方がよいとの意見。
- Evidence：
  - Transcript 00:32:43～00:33:08
- Reference：
  - 資料1 P.5
- 確実性：補完あり
```

------

# 40．論点別整理

M-IDを変更せず、必要に応じて論点別索引を作成できる。

例：

```
## 再任用職員の給与改定

- M-012
- M-013
- M-014
- M-021
```

------

# 41．Skill 04禁止事項

- 完成議事録の作成
- AI一般知識による補完
- 提案を決定へ昇格させること
- 意見を合意へ昇格させること
- Referenceだけによる意思決定認定
- 不明事項の推測
- 発言者の無根拠な推定

------

# 42．Skill 05：meeting-minutes-writer

## 42.1 目的

Skill 02～04の成果物および提供資料を参照して、読者向けの正式な議事録を作成する。

Skill 05は、

> **新しい事実を認定する工程ではなく、既に整理された議事内容を編集する工程**

である。

------

# 43．Skill 05の編集権限

以下を認める。

- M-IDの論点別再配置
- 関連M-IDの統合
- 重複内容の圧縮
- 見出し生成
- 小見出し生成
- 概要文生成
- 表・本文・Q&A等の形式選択
- 重要発言の強調
- 全体要約生成
- 正式表記への補正

------

# 44．統合ルール

複数M-IDを統合する場合、意味の差異を失わせてはならない。

特に、

- 立場
- 評価
- 条件
- 留保
- 賛否
- 懸念

が異なる場合、それらを一つの総意へ変換してはならない。

例えば、

```
A：賛成
B：慎重にすべき
C：条件付きなら可能
```

を、

> 実施する方向で意見が一致した。

と記載してはならない。

一方、

```
A自治体：未実施
B自治体：未実施
C自治体：未実施
```

について、

> 複数の自治体から未実施との報告があった。

と統合することはできる。

------

# 45．Skill 05における資料補完

Skill 05で資料を使用する目的は、

> **正式かつ正確な表記に整えること**

である。

例えば、

```
行一
```

を資料に基づき、

```
行政職俸給表（一）
```

と記載できる。

Skill 04：

> 何を意味していたか確定する。

Skill 05：

> それを正式・正確に表記する。

という責任分界を維持する。

------

# 46．発言者名

合理的に特定できる場合は、可能な限り発言者名を残す。

ただし、

**氏名を残すことより誤認防止を優先する。**

特定できない場合でも発言内容は削除しない。

必要に応じ、

- 参加者
- 話者不明
- 氏名省略

とする。

------

# 47．議事録標準構成

既存議事録の情報構造を参考として、原則以下を基本形とする。

```
会議名

基本情報

全体要約

主要テーマ・議題
 ├ 概要
 ├ 説明事項
 ├ 質疑応答
 ├ 主な意見・議論
 └ 必要に応じ重要発言

決定事項と今後の対応
```

会議の性格に応じ、不要な区分は省略する。

学習会、研修、座談会等を会議形式へ無理に当てはめてはならない。

------

# 48．構成原則

会議・行事全体の大きな流れについてはScene構造を参考にする。

各区分内部では、時系列よりも、

> **読者が理解しやすい論点・テーマ単位**

で再構成してよい。

元の時系列はM-IDによって保持する。

------

# 49．表示形式選択

## 説明・情報提供

原則：

```
見出し
↓
概要
↓
要点表または本文
```

## 質問・回答

原則：

```
【問】
...

【答】
...
```

またはQ&A表。

## 実態報告・意見交換

必要に応じ、

```
No. | 意見等
```

形式を使用する。

発言者を特定できる場合は氏名を残す。

## 重要発言

議論の趣旨を端的に示し、記録価値が高い発言については独立した強調表示を認める。

意味を変更してはならない。

------

# 50．各テーマの概要

各テーマの概要は、関連M-IDを統合し、

> **何について、どのような説明・議論が行われたか**

を簡潔に記載する。

概要で新しい結論を作ってはならない。

特に、

- 確認した
- 認識を共有した
- 合意した
- 決定した

等の表現には、対応するM-ID上の根拠を必要とする。

------

# 51．全体要約

全体要約は**本文完成後**に作成する。

主要な、

- 説明事項
- 論点
- 意見
- 確認・決定事項
- 今後の課題

を一読して把握できる程度に整理する。

本文の詳細を単純に再掲しない。

------

# 52．決定事項と今後の対応

標準形式：

```
区分 | 内容 | 担当・確認先 | 時期・期限
```

区分例：

- 確認
- 決定
- 要対応
- 継続課題
- 未決

Skill 04で対応するM-IDが確認できない事項を追加してはならない。

担当者・期限が不明な場合も推測しない。

------

# 53．Markdown仕様

議事録は標準的なMarkdownとして作成する。

CSSがなくても内容を理解できる状態を維持する。

例：

```
# 第1回○○会議

## 基本情報

| 項目 | 内容 |
|---|---|
| 日時 | 2026年○月○日 |
| 形式 | 対面・Web併用 |
| 参加者 | ○○ |

## 全体要約

- ○○
- ○○

# ○○について

## ○○の概要

**概要**　○○について説明が行われた。

| No. | 概要 |
|---:|---|
| 1 | ○○ |
| 2 | ○○ |

### 質疑応答

**問**　○○

**答**　○○

# 決定事項と今後の対応

| 区分 | 内容 | 担当・確認先 | 時期・期限 |
|---|---|---|---|
| 確認 | ○○ | ○○ | ○○ |
```

------

# 54．根拠IDの非表示保持

通常の議事録本文にはM-ID・S-IDを可視表示しない。

Markdown内部にHTMLコメントとして保持する。

例：

```
<!-- source: M-023, M-024 / S-007 -->
```

これにより、

```
議事録
↓
M-ID
↓
S-ID
↓
Transcript
↓

```

へ遡れるようにする。

# 55．CSS仕様

議事録本文とデザインを分離する。

`minutes.css`を作成し、少なくとも以下を規定する。

- A4縦
- 印刷用ページ余白
- 日本語文書向け本文サイズ
- 適切な行間
- H1～H3階層
- 見出し下罫線
- 表ヘッダー
- 表罫線
- セル余白
- 引用・重要発言枠
- 見出し直後の不自然な改ページ抑制
- 表の不自然なページ分割抑制
- PDF・印刷向け設定

既存議事録PDFのデザインを利用可能な場合は、これを標準デザインのリファレンスとして参照する。

ただし完全なピクセル単位の複製を目的とせず、情報階層・可読性・印刷適性を優先する。

# 59．ID管理の基本原則

S-IDおよびM-IDは根拠追跡のための重要な識別子である。

以下を守る。

- 一意であること
- 原則として時系列であること
- 後工程で不用意に変更しないこと
- 並べ替えを理由として再採番しないこと
- 既存参照を壊さないこと

```

```

# 61．補助スクリプト

本Skills群には、別途提供される、

**`validate_ids.py`**

を、

```
scripts/validate_ids.py
```

として配置すること。

このスクリプトは、本仕様書とともにAIへ提供されたファイルを原本として使用する。

**同等機能を理由なく再実装したり、内容を簡略化したりしない。**

必要なプラットフォーム適応がある場合のみ、原機能を保持したうえで調整する。

------

# 62．validate_ids.pyの目的

本スクリプトは、

1. S-IDの採番
2. M-IDの採番
3. S-ID重複確認
4. M-ID重複確認
5. ID順序確認
6. 欠番確認
7. 未採番プレースホルダー確認
8. M-IDからS-IDへの参照確認
9. 議事録sourceコメントからM-ID/S-IDへの参照確認

を補助する。

------

# 63．自動採番

安全な標準運用では、AUTOプレースホルダーのみを採番する。

例：

```
python validate_ids.py number 02_シーン構造分析.md --type scene
python validate_ids.py number 03_議事内容整理.md --type meaning
```

既存IDの再採番は通常運用では行わない。

------

# 64．ID点検

標準点検：

```
python validate_ids.py check \
  --scene 02_シーン構造分析.md \
  --meaning 03_議事内容整理.md \
  --minutes 04_議事録.md
```

## Skill 04完了後

# 77．品質基準

音声・提供資料の範囲を超えていない。

数字、日付、氏名、制度名等が確認されている。

## 意味保持

意見、提案、合意、決定等を混同していない。

## 不確実性保持

確認できない事項を断定していない。

## 可読性

逐語録ではなく、議事内容を理解しやすく再構成している。

## 追跡可能性

↓

↓
S-ID
↓
Transcript
↓
原音声

## 修正可能性

人間が各工程を確認・修正できる。

## 移植性

Core Skillsが特定プラットフォームへ過度に依存していない。

# 78．最終要確認事項

Skill 01は最終的に要確認事項を抽出する。

例：

```
## 最終確認が必要な事項

- M-032：発言者を特定できない。
- M-047：「確認する」との発言はあるが担当者が明示されていない。
- M-061：資料では9月、発言では10月となっている。
```

これにより、人間が音声全体を聞き直すのではなく、確認が必要な箇所へ集中できるようにする。

------

# 79．変更してはならない中核原則

実装AIは、プラットフォームへの適応や簡略化を理由として以下を変更してはならない。

1. 原音声・提供資料にない会議内容を創作しない。
2. 不明情報を推測によって確定しない。
3. 意見・提案・合意・決定を区別する。
4. 中間成果物を独立して保存する。
5. 根拠を追跡可能にする。
6. Skill 02～05の責任分界を維持する。
7. 読みやすさを理由として発言の意味を変更しない。
8. 人間が途中成果物を確認・修正できる構造を維持する。
9. プラットフォーム固有処理とCore Skillsを可能な限り分離する。
10. 長大な成果物は必要箇所を段階的に参照する。
11. 必要なEvidence確認をコンテキスト節約のために省略しない。
12. S-ID／M-IDの一意性・安定性・参照整合性を維持する。
13. ID等は将来的な機械検証が可能な程度に規則化する。
14. 自動処理できなかった工程を処理済みと偽らない。

CoreがChatGPT固有仕様に依存していないか。

議事録が逐語録ではなく、読者向けに適切に整理されるか。

# 87．完成判定

以下をすべて満たした場合に、本Skills群を完成とする。

- 5つのCore Skillsが存在する。
- 各Skillの責任範囲が明確である。
- 音声→Transcript→Scene→Meaning→Minutesの工程が成立する。
- 各工程の成果物が保存される。
- Evidence／Referenceが区別される。
- 不明事項を保持できる。
- 発言者を無理に推測しない。
- M-ID／S-IDによる追跡が可能である。
- `validate_ids.py`による検証が可能である。
- Markdown議事録が単独でも読める。
- CSSによるPDF・印刷向け体裁を適用できる。
- 中間成果物を人間が修正できる。
- 修正後、必要工程のみ再実行できる。
- ChatGPT固有処理がCoreから分離されている。
- Claude・Gemini等への移植を阻害する重大な依存がない。

# 88．最終目標

利用者がWork等へ、

- 録音
- 配布資料
- 必要に応じ参加者名簿等

を渡し、

> **「この録音と資料から議事録を作成して」**

と指示する。

これだけで統括Skillが必要な工程を判断し、

```
01_音声トランスクリプト.md
↓
02_シーン構造分析.md
↓
03_議事内容整理.md
↓
04_議事録.md
```

を順次作成する。

最終議事録は読み手にとって自然で簡潔な文書とする一方、その内部では、

```
議事録記述
↓
M-ID
↓
S-ID
↓
Transcriptタイムスタンプ
↓
原音声
```

まで遡ることができる。

そしてAIが確定できなかった事項については隠さず、

> **人間が確認すべき箇所**

として提示する。

本Skills群の最終的な価値は、AIによる完全自動化そのものではなく、

**「AIに議事録作成を任せながら、人間が根拠を確認し、必要な箇所だけ修正・判断できる議事録作成環境」**

を構築することにある。
