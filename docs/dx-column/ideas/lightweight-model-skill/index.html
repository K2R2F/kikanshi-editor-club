全部をエージェントにしなくてもいい

この着想の内容

  1. 次に試したいこと
  2. 留意事項
  3. 参考資料

クラウドで提供されるAIについて、「以前より期待した答えが返ってこない」と感じることがある。その体感だけで、AI全体の能力が低下したとは判断できない。同じ名称のサービスでも、更新や利用条件によって応答の傾向が変わる場合がある。

一方、費用や利用量を抑えるため、あえて軽いモデルを使いたい場面もある。

自ら手順を選び、ツールを使って仕事を進めるAIエージェントへの関心が高まるなか、従来のプロンプトによる仕事の教え方は、もう古いのだろうか。

必ずしもそうではない。定型的な仕事や繰り返し行う仕事なら、別の設計も考えられる。対象業務を絞り、手順や判断基準を再利用できる形にまとめたSkillに、禁止事項や正解例も記録する。ファイルの確認や件数の照合、処理順序、出力形式の検査はコードに任せる。そのうえで、軽量モデルには抽出、限定された分類、定型的な文章化などを担当させる。

判断が難しい案件や検査で問題が見つかった案件は、高性能モデルや人へ引き継ぐ。

すべての仕事を、一つの賢いAIに任せる必要はない。仕事を小さく分け、間違えてはいけない部分をコードで固めれば、軽いAIでも安定して働ける可能性がある。

これは、旧来のプロンプトへ戻るという話ではない。プロンプトをSkillとして再利用できる形にし、コードによる検査と、仕事に応じたモデル選択を組み合わせる。エージェント化が進むからこそ、こうした堅実な業務設計を、もう一度考えてみる価値がありそうだ。

次に試したいこと

検証の出発点として、同じ業務と原資料を用意し、次の三つを比較したい。

  1. 高性能モデルに、簡単な指示だけを渡す
  2. 軽量モデルに、詳細なSkillを渡す
  3. 軽量モデルに、Skillと検証コードを組み合わせる

比較するのは、完成文の読みやすさだけではない。事実の正確性、根拠の欠落、同じ入力に対する再現性、使用トークン、人が修正する時間、そして「静かな失敗」をどこまで発見できるかである。

まずはこの三つを比べ、必要に応じて高性能モデルにも同じSkillと検証コードを渡して、モデルの違いと設計の違いを分けて確かめたい。

高性能モデルと軽量モデルの差を、プロンプトとコードでどこまで埋められるのか。埋められないのは、どのような判断なのか。次は、実際のSkillを使って確かめてみたい。

留意事項

  • 応答が以前と違うという体感や個別事例だけでは、AIサービス全体の能力低下を判断できない。
  • ここで述べた業務への適用案は、参考資料を手がかりにした筆者の着想であり、研究によって直接実証された構成ではない。
  • 軽量モデルの性能は、対象業務、プロンプト、入力の長さ、利用できるツール、出力形式によって変わる。
  • 軽量モデルは、根拠が競合する判断、暗黙の文脈理解、未知の例外処理などでは、高性能モデルより不利になる可能性がある。
  • コードによる検査にも欠陥は起こり得る。Skill、コード、モデルを一体として評価する必要がある。
  • 参照した研究にはプレプリントや立場を提示する論文が含まれ、今後の査読や追試によって評価が変わる可能性がある。
